## Read-only Factory recovery

The Factory address contains a proxy shell. EIP-1967 implementation storage resolves to `0x74956236ab64ed143933040b4137e8a352e4d17b`; admin slot is zero and beacon slot is zero. The implementation bytecode exposes the `createCPU` selector and contains the `deploy fee` revert path. The fee value is recoverable from Factory storage slot `3` even though no verified public `deployFee()` getter was established.

The original fresh simulation used these exact values; the labels `fee-1` and `fee` must not be attached to the middle two values because the current fee has one additional zero:

| `msg.value` | `eth_call` | `eth_estimateGas` |
|---:|---|---|
| `0` | revert: `deploy fee` | revert |
| `659999999999999` | revert: `deploy fee` | revert |
| `660000000000000` | revert: `deploy fee` | revert |
| `6600000000000001` | success; returned Processor/transistor addresses | success |

The current slot-3 boundary was then checked explicitly with the same read-only test calldata:

| `msg.value` | `eth_call` | `eth_estimateGas` |
|---:|---|---|
| `6600000000000000` (exact slot 3) | success | success |
| `6600000000000001` (slot 3 + 1 wei) | success | success |

Therefore the current createCPU payment boundary is `msg.value >= 6600000000000000 wei` (`0.0066 OKB`). The earlier `fee-1`/`fee` labels were a transcription/zero-count error; the raw slot value and the four original simulation inputs were not changed. This proves the current read-only simulation boundary; it does not authorize a write or freeze future fee changes.

## Boundary classification

### A. Must close BEFORE `createCPU`

1. Chain ID must be `196`.
2. Factory address and code must match the frozen address.
3. Final `name`, `symbol`, `story`, `supplyCap`, and `mintPrice` must be supplied by the Product Owner; this is a decision requirement, not an unresolved protocol fact.
4. Immediately before signing, read Factory implementation/fee state again and simulate the exact final calldata with the exact sender.
5. The simulation must return success and `eth_estimateGas` must succeed with the chosen `msg.value`.
6. Product Owner must explicitly accept that Processor/transistor beacons are Factory-owned upgrade trust boundaries.

No mint formula, tape-out fee, or universal NAND relationship is required to be proven before preparing this first Factory write. Those belong to later transaction boundaries or disclosure.

### B. Must close AFTER `createCPU` but BEFORE transistor mint

These are instance-specific checks against the newly emitted addresses:

- Processor and transistor code exists;
- `CPUCreated` event addresses match the returned/recorded addresses;
- exact `supplyCap()`, `mintPrice()`, `protocolFee()`, `minted()`, and primitive IDs are recorded;
- exact `mint(0, N)` calldata is simulated with `eth_call` and `eth_estimateGas`;
- exact mint `msg.value` is established from that simulation and current instance state;
- caller balance and expected post-mint balance are verified before signing.

This is the correct boundary for the unknown mint payment formula and `protocolFee` settlement. They are not pre-`createCPU` blockers because the exact new transistor does not exist until Factory creation succeeds.

### C. Must close BEFORE tapeout

- Exact frozen netlist bytes, input count, output count, and SHA-256;
- exact Circuit transistor quantity and pre-tapeout balance;
- exact tape-out `msg.value` from simulation/estimate for the new Processor;
- expected burn event, Circuit mint event, `TapedOut` event, and Circuit ID decoding;
- an explicit decision on the current Processor/beacon upgrade risk if it was not accepted at deployment.

The exact tape-out fee is therefore a **PRE-TAPEOUT BLOCKER**, not a pre-`createCPU` blocker.

## Upgrade/admin risk: informed consent level only

### FACT

- The Processor and transistor are beacon-proxy based in the observed historical system.
- The Processor beacon and transistor beacon `owner()` both return the Factory.
- The Factory has an implementation upgrade boundary; the Processor/transistor implementation can therefore change under Factory-controlled authority.
- No claim of permanent immutability is supported.

### What cannot currently be proven

- The full Factory owner/admin governance process;
- whether and when Factory/beacon upgrades can change fees, token accounting, tapeout behavior, or metadata behavior;
- Processor-specific seal/freeze semantics;
- long-term compatibility of future implementations.

### Product Owner risk acceptance

Before `createCPU`, the Product Owner must accept that the Processor is an upgradeable protocol instance, not a cryptographically immutable economic contract. GateSmith may disclose the deployed implementation/beacon addresses and the read-time values, but must not promise:

- immutable supply or price;
- immutable mint/tapeout semantics;
- immutable evaluation behavior without an upgrade/admin qualification;
- that current historical fee observations are permanent.

This is an informed-consent requirement, not a request for a full protocol audit before the first write.

## First-write checklist

The first Factory write is ready to prepare once the Product Owner supplies parameters, subject to this final pre-sign sequence:

1. Confirm wallet network is X Layer chain `196`.
2. Read Factory code and implementation/fee state.
3. Encode the final `createCPU` calldata.
4. Read current deploy fee slot `3`.
5. Choose `msg.value` at least equal to the current fee, then run `eth_call` and `eth_estimateGas` with the exact sender, calldata, and value.
6. Confirm estimated gas and protocol payment separately.
7. Present the complete packet to the Product Owner for manual wallet confirmation.
8. After signing, verify receipt, `CPUCreated`, Processor code, transistor code, and getters before preparing any mint transaction.

Any failed read, simulation, receipt, event, code, or getter check is a hard stop. No subsequent transaction is automatically prepared.
